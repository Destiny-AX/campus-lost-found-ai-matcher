# 拾寻 v3 体验升级实施计划

## 一、Summary（概述）

本次升级围绕 7 个核心方向优化"拾寻"城市失物招领平台，在保持现有核心功能稳定的前提下，提升界面美观性、用户参与感、信息过滤效率和防冒领安全性。

**关键决策汇总：**
| 方向 | 决策 |
|------|------|
| 成就感/互动感 | 先做轻量级成长体系（等级+徽章+统计），卡通小人作为二期 |
| 地图展示 | 暂不实现，优先做结构化地点+级联筛选 |
| 高匹配提醒 | 移除右侧固定面板，改为浮动通知气泡 |
| 地域筛选 | 发布时强制选择城市→区→街道（具体位置选填） |
| 认领问答 | 拾到者发布时设置选填问题，失主回答后拾到者人工审核 |
| 诚信校验 | 认领问答 + 双向评价举报，形成信用闭环 |

## 二、Current State Analysis（现状分析）

### 2.1 技术架构
- **前端**：纯 HTML+CSS+JS SPA，无框架依赖，单文件 `script.js`（约 2500 行）
- **后端**：Vercel Serverless Functions（Node.js 原生），零 npm 依赖
- **数据库**：Supabase PostgreSQL，含用户表、记录表、代保管点表、通知表、信用日志表
- **认证**：自实现 HS256 JWT，支持微信 Mock 登录和游客登录
- **AI**：SiliconFlow API（Qwen3-VL-8B 视觉模型、Qwen3-8B 文本模型）

### 2.2 现有功能盘点

**已有且稳定：**
- 失物/招领信息发布（含 AI 智能结构化输入）
- 7 维度 AI 匹配算法（类别+颜色+地点+时间+文本+图像+语义）
- 三层隐私模糊化（未认证用户看不到完整信息）
- 物品状态分流（原地/代保管/已交机构/不确定）
- 代保管点 + 6 位取件码安全交接
- 公共机构对接（派出所/地铁失物中心等）
- 通知中心（8 秒轮询）
- 基础用户资料页（信用积分 5/10、1-2 个静态徽章）
- 数据概览页（发布总数、今日新增、高匹配线索、语义识别记录）

**现有问题：**
- 右侧 `inspector` 面板始终显示高匹配提醒，对所有用户造成信息干扰
- 地点字段是纯文本 `"南京东路地铁站"`，无法按区域层级筛选
- 用户成长体系极其简陋（只有静态积分和 2 个徽章）
- 无防冒领的二次验证机制（仅靠实名认证门槛）
- 界面美观度有提升空间（无动画反馈、无加载状态、无空状态插画）


## 四、Assumptions & Decisions（假设与决策）

| # | 决策 | 理由 |
|---|------|------|
| 1 | 卡通小人作为二期 | 用户确认先实现成长体系，小人需要设计资源，后续可追加 |
| 2 | 地图展示暂不实现 | 用户确认优先做结构化地点+筛选，地图开发成本高且信息密度难控 |
| 3 | 地点级联选择先只支持上海 | 当前数据全部是上海，其他城市可后续扩展 |
| 4 | 认领问答由拾到者人工审核 | 用户明确选择，比 AI 自动判断更可靠 |
| 5 | 经验值和等级纯前端计算 | 减少后端改动，等级公式简单，前端可实时计算 |
| 6 | 浮动通知用 localStorage 去重 | 避免重复通知同一匹配，简单有效 |
| 7 | 评价系统只在认领完成后触发 | 避免未交易就评价，保证评价真实性 |

按依赖关系和用户体验影响排序：

### Phase 1：基础框架（无依赖，可并行）
1. **数据库 Schema 更新**（`supabase-schema.sql`）
2. **界面美观性升级**（`style.css` 动画 + `script.js` 加载状态）
3. **移除右侧 Inspector + 浮动通知**（`index.html`, `style.css`, `script.js`）

### Phase 2：核心功能（依赖 Phase 1）
4. **地域结构化 + 级联筛选**（`index.html`, `script.js`, `api/records.js`, `api/structured-input.js`）
5. **成长体系**（`api/auth.js`, `script.js`, `index.html`）

### Phase 3：安全与信任（依赖 Phase 2）
6. **认领问答系统**（`index.html`, `script.js`, `api/records.js`）
7. **双向评价 + 举报**（`index.html`, `script.js`, `api/records.js`）

### Phase 4：收尾
8. **界面简化与调优**（`index.html`, `script.js`, `style.css`）
9. **端到端测试 + Vercel 部署**

## 六、Verification Steps（验证步骤）

### 6.1 功能验证清单

| 功能 | 验证步骤 |
|------|----------|
| 加载动画 | 刷新页面，确认有骨架屏/加载遮罩 |
| 卡片动画 | 滚动失物广场，确认卡片有 stagger 入场动画 |
| 浮动通知 | 以未认证用户发布寻物信息，等待匹配后确认右下角出现通知气泡 |
| 地域筛选 | 发布时选择区→街道，发布后确认筛选器可按区/街道过滤 |
| 成长体系 | 发布一条信息，确认首页状态条 EXP 增加，等级可能变化 |
| 徽章解锁 | 完成实名认证，确认徽章列表新增"✅ 实名认证" |
| 认领问答 | 发布时设置问题，用另一账号申请认领，确认需要回答问题 |
| 审核流程 | 发布者收到认领通知，点击同意后申请者看到联系方式 |
| 评价系统 | 认领完成后，双方确认可互相评价 |
| 举报机制 | 点击举报按钮，确认被举报用户信用分下降 |

### 6.2 回归测试
- 旧数据兼容性：未结构化地点的旧记录仍能正常显示和搜索
- 认证流程：微信登录、游客登录、实名认证不受影响
- 匹配算法：7 维度匹配仍正常工作
- 代保管流程：取件码系统不受影响
- 移动端：所有新功能在移动端正常可用

## 七、Risk & Mitigation（风险与缓解）

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| `script.js` 文件过大 | 维护困难 | 本次仍保持单文件，但按模块用注释分隔，为后续拆分做准备 |
| 数据库迁移失败 | 旧数据丢失 | 所有 ALTER 都带 `IF NOT EXISTS`，新增字段有默认值 |
| 地点结构化导致旧数据不匹配 | 筛选时旧记录消失 | 旧记录的 `district`/`street` 从 `location` 文本反向解析，或标记为" legacy " |
| 认领流程增加使用门槛 | 用户流失 | 认领问题为选填，不设置也能正常发布 |
| 评价系统被滥用 | 恶意差评 | 限制每人每条记录只能评价一次，举报需理由 |
