# 拾寻 v2 — 城市级失物招领 AI 智能匹配平台 实施计划

## 一、项目愿景与定位

**从"校园失物招领"升级为"城市拾遗网络"**——一个覆盖城市公共空间的失物智能匹配平台，融合 AI 语义识别、隐私模糊化、实名认证、代保管流转和信用激励，让每一件遗失物都有回家的路。

- **项目性质**：课堂 demo 优先，架构预留城市级扩展空间
- **技术载体**：H5 响应式 Web App（延续当前架构）
- **核心创新点**：AI 自然语言结构化输入 + 三层信息模糊化 + 物品状态分流 + 代保管取件码 + 信用积分

## 三、当前状态分析

### 3.1 现有架构
- **前端**：单页 SPA，原生 HTML/CSS/JS，script.js 约 1242 行（全部业务逻辑）
- **后端**：Vercel Serverless Functions（api/records.js + api/analyze-image.js）
- **数据库**：Supabase Postgres，单表 `lost_found_records`，无 owner 字段、无 RLS
- **AI**：SiliconFlow Qwen3-VL-8B-Instruct 视觉模型
- **本地服务**：local-server.js（端口 4173），内嵌了 analyze-image 副本

### 3.2 关键缺陷
1. **无账号系统**：删除靠 localStorage，无用户身份
2. **无隐私保护**：所有信息全量公开，存在"藏宝图"风险
3. **无物品状态**：只有 lost/found 两种类型，无流转状态
4. **无通知机制**：匹配成功后无任何推送
5. **输入流程繁琐**：需手动填写 6+ 字段
6. **script.js 过大**：1242 行单文件，维护困难
7. **移动端体验一般**：三栏布局在小屏上信息密度过高

## 五、功能模块详细设计

### 5.1 AI 自然语言结构化输入

**流程**：
1. 用户在"智能输入框"输入自然语言，如："昨天下午3点左右在南京路地铁站丢了一个黑色双肩包，里面有笔记本电脑"
2. 前端调用 `POST /api/structured-input`
3. 后端调用 SiliconFlow 文本模型（Qwen3-8B-Instruct），prompt 要求提取：
   - `type`: lost / found
   - `category`: 电子产品/箱包/证件/...
   - `color`: 颜色
   - `location`: 地点
   - `time`: 时间
   - `description`: 描述
   - `item_status`: 物品状态推断
4. 返回结构化 JSON，前端自动填充表单各字段
5. 用户确认/修改后提交

**API 设计**：
```
POST /api/structured-input
Body: { "text": "昨天下午3点左右在南京路地铁站丢了一个黑色双肩包" }
Response: {
  "type": "lost",
  "category": "箱包",
  "color": "黑色",
  "location": "南京路地铁站",
  "time": "2026-05-28T15:00",
  "description": "黑色双肩包，内有笔记本电脑",
  "item_status": "unknown",
  "confidence": 0.92
}
```

### 5.2 三层信息模糊化

**模糊规则**：

| 字段 | 模糊化策略 | 解锁条件 |
|------|-----------|---------|
| 位置 | "XX路附近 500m" / "XX区" | 双方实名握手 |
| 时间 | "上午" / "下午" / "晚上" / "昨天" | 双方实名握手 |
| 联系方式 | 完全隐藏，显示"实名后查看" | 双方实名握手 |
| 描述 | 保留类别+颜色，隐藏品牌/型号/特殊标记 | 双方实名握手 |
| 图片 | 缩略图 + 高斯模糊 | 双方实名握手 |

**实现**：
- `privacy.js`：`fuzzifyRecord(record)` → 返回模糊化版本
- `privacy.js`：`canUnlock(record, currentUser)` → 判断是否可解锁
- 后端 `records.js` GET 接口：根据请求者身份返回模糊/完整数据
- "握手"流程：匹配双方都点击"确认身份"后，互相解锁对方信息

### 5.3 Mock 微信登录 + Supabase Auth

**流程**：
1. 首页显示"微信登录"按钮（绿色，带微信图标）
2. 点击后弹出模拟 OAuth 窗口（显示微信风格授权页）
3. 用户输入昵称 + 选择头像 → 后端创建 Supabase Auth 账号
4. 返回 JWT token，前端存入 localStorage
5. 后续请求携带 Authorization header

**预留接口**：
- `auth.js` 中 `WECHAT_OAUTH_URL` 常量，当前指向 mock，生产环境替换为真实 URL
- `api/auth.js` 中 `verifyWechatCode()` 函数，当前返回 mock 用户，生产环境调用微信 API

### 5.4 站内实时通知（SSE）

**架构**：
- `api/notify.js`：Vercel Serverless Function，建立 SSE 连接
- `notify.js`（前端）：EventSource 连接，收到消息后：
  - 更新通知铃铛数字
  - 弹出 toast 提示
  - 存入本地通知列表

**通知触发场景**：
1. 新匹配产生（匹配度 ≥ 75%）
2. 对方确认身份（握手成功）
3. 代保管寄存确认
4. 取件码生成
5. 信用积分变更

**SSE 消息格式**：
```json
{
  "type": "match_found",
  "title": "发现高匹配线索",
  "body": "您发布的'黑色双肩包'与一条招领记录匹配度达 87%",
  "related_record_id": "record-xxx",
  "created_at": "2026-05-29T10:00:00Z"
}
```

> 注意：Vercel Serverless 有执行时长限制（免费版 10s），SSE 长连接需改用轮询或 Vercel Edge Functions。demo 阶段可用短轮询（5s 间隔）模拟实时效果。

### 5.5 物品状态分流

**发布时选择状态**：
- 📍 仍在原地 → 显示导航按钮（跳转地图 App）
- 🤝 被他人保管 → 显示保管者信息（模糊化）+ "联系保管者"按钮
- 🏛️ 已交公共机构 → 显示机构名称 + 认证标签 + 联系方式
- ❓ 不确定 → 默认模糊化展示

**状态流转**：
```
发布(unknown) → 目击者更新(in_place/custody) → 拾到者确认(picked/institution)
```
- 任何登录用户可"更新状态"（需选择新状态 + 可选留言）
- 状态变更记录存入 `notifications` 表

### 5.6 代保管完整流程

**流程**：
1. 拾到者发布招领时选择"寄存到代保管点"
2. 选择附近代保管点（从 `custody_points` 表加载）
3. 系统生成 6 位取件码（数字+字母，避免易混淆字符）
4. 拾到者将物品送至代保管点，出示取件码前半部分
5. 代保管点确认寄存 → 通知失主
6. 失主凭取件码后半部分取件
7. 取件成功 → 双方信用积分 +10

**取件码设计**：
- 格式：`XX-XXXX`（2位寄存码 + 4位取件码）
- 寄存码给拾到者看，取件码给失主看
- 任一方单独无法取件（安全设计）

### 5.7 信用积分 + 徽章

**积分规则**：
| 行为 | 积分 |
|------|------|
| 发布真实信息 | +5 |
| 成功归还物品 | +10 |
| 代保管点寄存 | +5 |
| 被举报（核实后） | -20 |
| 每日登录 | +1 |

**徽章系统**：
| 徽章 | 条件 |
|------|------|
| 🌱 新手上路 | 首次发布 |
| 🔍 拾金不昧 | 成功归还 1 件 |
| ⭐ 热心市民 | 成功归还 5 件 |
| 🏅 城市好心人 | 成功归还 20 件 |
| 🏛️ 官方认证 | 机构账号 |

### 5.8 移动端优化

**核心改动**：
1. **底部 Tab 导航**：首页 / 发布 / 消息 / 我的（替代当前侧边栏）
2. **卡片流布局**：单列瀑布流，减少信息密度
3. **智能输入优先**：移动端默认展开"说一句话描述"输入框，表单折叠
4. **触摸优化**：增大点击区域、滑动操作（左滑删除、下拉刷新）
5. **图片压缩增强**：移动端压缩至 640px / JPEG 0.7
6. **骨架屏**：加载时显示骨架占位，减少白屏时间
7. **PWA 支持**：添加 manifest.json + Service Worker，支持添加到主屏幕

## 八、风险与缓解

| 风险 | 缓解措施 |
|------|---------|
| Vercel Serverless SSE 超时 | demo 阶段用短轮询（5s），路线图标注 Edge Functions |
| SiliconFlow API 限流 | 结构化输入加前端防抖（1s），失败回退手动填写 |
| Supabase RLS 配置复杂 | 先用应用层鉴权，RLS 作为增强层 |
| script.js 拆分引入模块兼容问题 | 使用 `<script type="module">`，所有现代浏览器支持 |
| Mock 登录安全性 | 仅 demo 用，生产环境必须替换为真实 OAuth |
| 取件码碰撞 | 6 位码空间 36^6 ≈ 21 亿，加唯一约束 + 重试 |
