# 文本模型 AbortError 根因分析

## 结论

已定位到的直接原因是应用自身的超时预算冲突，不是“Vercel Function 必然超时”：旧实现允许主模型约 25 秒后再调用备用模型约 25 秒，最坏路径接近 50 秒；前端却在约 30 秒主动 `AbortController.abort()`。当 SiliconFlow 单次响应较慢时，浏览器先中止请求，页面看到 `AbortError`，服务端随后才可能进入或完成第二次调用。

历史线上观察中，出现过单次模型约 17.7 秒成功，也出现过整条链路约 55 秒后落到规则兜底。这说明供应商响应慢是触发条件，应用端总预算与浏览器预算不一致是可复现的工程根因。样本很少，不能据此声称供应商稳定性水平。

## 排查矩阵

| 候选原因 | 结论 | 证据 / 处理 |
|---|---|---|
| 浏览器主动中止 | 已确认是表层错误来源 | 前端存在固定 AbortController 时间限制，旧服务端最坏耗时超过它 |
| Vercel Function 超时 | 未确认 | 没有 Function 日志证明平台先终止；旧链路本身已可超过前端预算 |
| 应用代码超时 | 已确认 | 旧主/备模型各自独立等待，缺少共享总预算 |
| SiliconFlow 响应过慢 | 已观察为触发条件 | 少量真实调用出现十几秒成功与长耗时失败；不外推为正式指标 |
| 主模型不可用 | 未确认 | 无连续 provider_status 样本支持该结论 |
| JSON 解析失败 | 不是本次 AbortError 根因，但已覆盖 | 新代码单独记录 `parse_status`，解析失败可降级一次 |
| 429 / 5xx / 网络 | 未在本次历史 AbortError 中确认 | 新代码将其分类为可重试临时错误，并最多降级一次 |

## 修复策略

1. 使用 28 秒共享总预算，不让两次调用各自无限占满预算。
2. 主模型默认 18 秒，备用模型最多使用剩余预算且默认上限 9 秒。
3. 仅对超时、网络、429、5xx、空响应或解析失败做一次模型降级；普通 4xx 不重试。
4. 两次均失败后明确返回 `source=heuristic_fallback`，不计作模型成功。
5. 前端等待预算略高于服务端总预算，并展示 request_id、来源、模型、耗时、尝试次数、provider/parse 状态和降级原因。
6. attempts 只保存分类状态和耗时，不保存 Key、完整用户原文或供应商原始响应。

## 仍需线上验证

需要在带独立 Preview 模型变量、且无需接触生产 Cookie/JWT 的环境中做 5—10 次固定非隐私输入调用，才能计算 P50/P95 与真实 AI/降级/规则次数。本轮没有这样的隔离凭证，因此没有把 Mock 场景延迟伪装成线上稳定性指标。
